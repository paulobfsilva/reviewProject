==========================================================================================
PART A. WHAT THE REVIEWS SHOW (translation problems seen in published translations)
==========================================================================================

Reviewed so far, block by block, on translators.messagehub.info:
65-1204 The Rapture, 60-0802 El Shaddai, 60-0723 Speak To The Rock,
60-0731 Show Us The Father, 60-0803 Abraham.

The same error families come back in every sermon, roughly in this order of impact:

A1. Bible quotations "completed" from memory (highest impact, every sermon)
    - ARC wording added where he did not say it (Rev 3:20 "Eis que… em sua casa… com ele",
      John 6:44 "que me enviou", John 14:12 "Aquele que crê em mim").
    - Verses reordered into ARC order (Rev 3:17, Gen 22:8), his ellipses removed.
    - His person/number/tense changed ("you" → "alguém", "said" → "diz", "words" → "palavra").
    - His explanation broken ("since you believed" → "quando crestes").
    Root cause: the model recognises the verse and reproduces the canonical text. A prompt
    rule alone does not stop this; the model needs the KJV text and the "what he actually
    said" diff in front of it, per quote.

A2. Forms of address drift across blocks
    - Same prayer-line person: você in one block, tu in the next; the interpreter as
      "Disseste" then "Diga"; the Voice in a vision as "você"; audience as "vós"/"sabes".
    Root cause: each paragraph is translated in isolation (see B1), so the model cannot
    know who was being addressed two blocks earlier.

A3. Term inconsistency across blocks
    - bumping: bater / embate / toque / barulho; balconies: varandas / piso superior;
      one hymn refrain translated four different ways; seed: semente / descendência.
    Root cause: same as A2 — no sermon-level memory.

A4. Meaning errors in the life stories (idioms and polysemy)
    - school me → "ensinar-me"; discharged → "dispensada"; speaker → "altifalante";
      footboard/headboard swapped; Indian → "Indiana"; saplings → "arbustos";
      impersonal "they send" → "vocês enviam"; third-person "let him sit" → "deixem-Me".
    Root cause: literal, sentence-local translation; no second pass that asks
    "does this make sense in the story?".

A5. Mechanical rule violations (easy to detect automatically, still frequent)
    - "porque…?" in questions, "acreditar", gerunds, "Oh" dropped from "Oh, bem",
      proclisis after subject pronouns, -lo/-la contractions, simple future,
      Brazilianisms (meio que, chamado, depois que), AO spellings (Laodicéia, impôr, Jacó),
      translator notes "[… - Trad.]", unconverted miles.
    Root cause: no deterministic linter between the model output and the human.

A6. Formatting fidelity
    - EN line breaks merged in PT (most frequent formatting error), ellipses added at
      block boundaries, quotes added at block end, dash spacing.
    Root cause: no structural check (line count per block) after generation.

PART B. WHAT THE CURRENT PIPELINE DOES (and why it produces Part A)
==========================================================================================

Current flow (README + scripts/process_sermon.py):
  fetch_sermon.py  →  input/en/<id>.txt
  process_sermon.py:
     1. translate title and place with the full system prompt (gpt-4o, T=0)
     2. translate EACH PARAGRAPH SEPARATELY with translate_system.txt (no context)
     3. post-edit each paragraph with a fine-tuned gpt-4o-mini
        (ft:gpt-4o-mini-2024-07-18:personal:pe-sermons-v2) + 3 TM examples from Chroma,
        using postedit_instructions.txt (5 generic lines; knows none of the rules)
     4. if PE is <85% of RAW length → retry, then fall back to RAW
     5. write output/raw, output/final, output/metadata/<id>.jsonl
  review/build_docx.py → .docx for human review → pasted into messagehub by hand.

Findings from reading the code:

B1. Paragraph-isolated translation (process_sermon.py, chat_translate per paragraph).
    Direct cause of A2 and A3, and contributes to A1 (no surrounding context to tell a
    quote from commentary when a quote spans blocks).

B2. The post-editor is rule-blind and can undo the rules.
    - postedit_instructions.txt does not contain any of the translation rules.
    - It is a fine-tuned mini model trained on data/pe_ft_train.jsonl (older human
      translations). TM examples from data/corpus.jsonl may contain the very forms the
      rules now forbid (acreditar, ARC completions, "Porque…?"). Nothing filters them.
    - Its system message is a one-liner; the RAW output of the strong model is "corrected"
      by a weaker model that has never seen the rules.
    → Needs measuring (Phase 0) before deciding to keep, retrain, or drop it.

B3. The QA package is mostly empty or broken.
    - Empty files (0 lines): qa/adequacy.py, heuristics.py, io_helpers.py, lt_check.py,
      run_qa.py, scoring.py, units.py; config/glossary.json and config/pre_ao_map.json
      are 0 bytes.
    - qa/bible.py: reads config/qa.yaml with json.loads (it is YAML → crash); the bible
      keys live in config/qa/qa.yaml, not config/qa.yaml (two qa.yaml files);
      config/book_map.json is invalid JSON (contains a /* … */ comment) and uses
      Brazilian spellings (Gênesis, Deuteronômio → PE: Génesis, Deuteronómio);
      the SQL (verse/book join) does not match the schema declared in qa/qa.yaml
      (table "verses"); only single-verse refs are checked.
    - More importantly, bible.py's LOGIC rewards a PT paragraph that contains the full
      ARC verse. That is the opposite of rule 2 (only the segments he said). It would
      push translations toward error A1. It must be redesigned, not just fixed.
    - lean_checks.scripture_refs looks for the ENGLISH reference string ("John 3:16")
      inside the Portuguese text → always flags. Coverage check compares PE with RAW,
      not with the English source.
    - lean_checks has no line-count check, no forbidden-forms check beyond AO spellings.

B4. Input parsing risks (to verify with tests).
    - utils.split_numbered_paragraphs starts a new paragraph on ANY line matching
      "^\d+\s" — a read-aloud scripture line that begins with a verse number
      ("16 For God so loved…") or a line like "3 o'clock" inside a block would be cut
      into a fake paragraph.
    - fetch_sermon.py uses get_text('\n'): inline tags (<i>, <a>, <span>) may create
      line breaks that are not real EN line breaks, which then become "line breaks the
      PT must keep".
    - The header translation goes through the full sermon prompt; the official PT title
      already exists on messagehub (e.g. "Abraão") and could be fetched instead.

B5. Models and cost.
    - translate_model gpt-4o (2024), temperature 0. The 18 KB system prompt is re-sent
      for every paragraph (≈85–200 calls per sermon) — acceptable only with prompt
      caching; a windowed approach (Part C) reduces calls.
    - Models should be configurable per stage so the pipeline can be benchmarked on
      newer/stronger models without code changes.

B6. Two sources of truth for rules.
    - Rules live in prose (translate_system.txt) and, separately, in the reviewer skill's
      regex scan. Neither the pipeline nor the corpus uses them. Every new review finding
      has to be added by hand in several places.

==========================================================================================
PART C. RECOMMENDED TRANSLATION FLOW
==========================================================================================

Principle: let the model translate with full context, then catch everything that can be
caught mechanically, then send ONLY the problem blocks back with the specific problem,
then give the human a short, prioritised report — and feed the human's corrections back.

  0. FETCH       EN text + metadata (+ official PT title/place if it exists).
                 Validate block numbering and line structure.

  1. ANALYSE     One pass over the whole sermon (LLM + deterministic help) producing a
                 "sermon sheet" (JSON):
                   - Bible quotes per block: detected passage, KJV text, and a
                     segment diff "said = KJV" / "his own words" / "KJV not said";
                     ARC text only for the "said = KJV" segments.
                   - Addressees per block/scene: audience / person in line (você) /
                     interpreter (você) / God (Tu) / Satan (tu) / characters (tu) /
                     Voice in vision (tu).
                   - Recurring terms and hymn lines (first rendering fixed here).
                   - Measurements to convert; proper names not to translate.

  2. TRANSLATE   Windowed: block N is translated with
                   - the system prompt (cached),
                   - the sermon sheet slice for block N (quotes, addressee, terms),
                   - the previous 2 blocks EN+PT (already translated) and next block EN,
                   - output = block N only, same line count.
                 Blocks can be done in sequential batches (e.g. 5 blocks per call) to
                 cut calls while keeping the "same block in, same block out" contract.

  3. LINT        Deterministic Python checks (no LLM), per block:
                   structure  : line count EN = PT, numbering, ellipses at block edges,
                                quotes balance, brackets, dash spacing, notes "Trad.";
                   rules      : forbidden-forms list (single machine-readable file),
                                "Oh, my"/"Oh, bem" counts, gerunds outside quotes,
                                proclisis after subject pronouns, -lo/-la, AO list;
                   measures   : miles/feet/°F left unconverted;
                   bible      : PT contains ARC words in segments marked "KJV not said".
                 Safe, unambiguous fixes are applied automatically and logged
                 (Laodicéia→Laodiceia, impôr→impor, Davi→David, Jacó→Jacob, "[… - Trad.]" removed).

  4. REVISE      Only flagged blocks go back to the main model with: EN block, PT block,
                 the exact list of findings, and "change only what is listed; return the
                 whole block". Re-lint. Max 2 rounds, then leave it for the human.
                 (The rule-blind fine-tuned post-editor is retired from this path unless
                 Phase 0 shows it improves quality.)

  5. REVIEW      LLM review pass equivalent to the sermon-translation-review skill
                 (checks A–K: meaning, Bible, address, consistency…) over the final text,
                 producing the same report format as the manual reviews:
                 output/review/<id>_report.md + a short "must fix" list.

  6. HUMAN       docx/messagehub as today, but the reviewer starts from the report.

  7. LEARN       When the human-approved PT is available (export from messagehub):
                   - diff machine-final vs human-final per block;
                   - classify each change (Bible / address / glossary / meaning / format);
                   - propose additions to rules.yaml + translate_system.txt (human approves);
                   - add the approved sermon to the TM corpus (only after it passes lint).

PHASE 3 — Bible quote handling (the main quality lever) (~3 days)
------------------------------------------------------------------------------------------
3.1  scripts/bible/detect.py — find quotes in EN blocks:
       a) explicit refs (John 6:44, "Revelation 3:20", "in Saint John the 6th chapter");
       b) block type "scripture" from fetch JSON;
       c) fuzzy n-gram match of EN sentences against KJV (rapidfuzz partial_ratio on
          normalised text, sliding window) to catch unreferenced quotes;
       d) frequent-verse list (config/rules/bible_traps.yaml, seeded from
          translate_system.txt §2 traps).
     Output per quote: block, char span, ref, his_text, kjv_text.
3.2  scripts/bible/segment_diff.py — align his_text vs kjv_text at phrase level
     (difflib on tokens, then merge into phrases): label each phrase
     SAID_AS_KJV | HIS_OWN | KJV_NOT_SAID; attach the corresponding ARC phrase for
     SAID_AS_KJV phrases only (word alignment KJV↔ARC is approximate: give the ARC verse
     and the KJV phrase and let the model pick, but list KJV_NOT_SAID phrases explicitly
     as "must not appear").
3.3  Bible guidance text injected into the translation prompt per block, e.g.:
       QUOTE Rev 3:20 — he says: "I stand at the door and knock: if any man hear my
       voice, and open, I'll come in and sup". KJV phrases he did NOT say: "Behold",
       "with him, and he with me". ARC verse for wording reference: "…". Translate only
       what he said, in his order.

3.5  Tests from fixtures: Rev 3:20 (60-0803 §49, §54), Rev 3:17 (§44), John 6:37

------------------------------------------------------------------------------------------
ORDER, DEPENDENCIES, RISKS
------------------------------------------------------------------------------------------
Order: 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7. Phase 2 (linter) gives value on its own and can be
used on human translations immediately; do it before any model changes.

Risks and mitigations
- KJV↔ARC phrase alignment is imperfect → never auto-insert ARC text; only use it as
  guidance and as a "must not appear" list for KJV_NOT_SAID phrases.
- Regex false positives (e.g. "porque" in causal clauses, gerunds inside Bible quotes)
  → severity levels, Bible-span scoping from Phase 3, and a per-rule allowlist.
- JSON-mode responses can truncate on long blocks → per-block retry and line-count
  validation; batch size configurable.
- Cost increase from context windows → prompt caching for the system prompt, batches of
  blocks per call, and the review pass only on final text.
- Rules drift between prose prompt and rules.yaml → sync test (7.5) and prompt hash in
  metadata (4.5).

Definition of done (whole project)
- One command produces: final PT, lint findings, review report, docx with comments.
- On the regression set: 0 line-count mismatches; 0 high-severity lint findings in the
  final text; Bible fixture findings ≤20% of baseline; address/consistency findings
  ≤30% of baseline.
- README documents the flow; tests pass.
